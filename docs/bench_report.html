What this is

Eight phases, six built and verified

MiniXLA takes a small tensor-op graph, rewrites it (constant folding, dead-node elimination, operator fusion into matmul+epilogue kernels), emits PTX for the fused regions, and runs it through the CUDA Driver API — with module caching and per-shape tile autotuning. Phase 6 adds reverse-mode autodiff on top.

Correctness

26 tests, run against real hardware, not mocked

18 CPU tests (gcc, includes a ptxas-validated codegen check) and 8 GPU tests (nvcc, actually execute generated PTX on the RTX 4060 and compare against the CPU reference to 1e-4–1e-2 depending on scale). Every number in this report comes from a binary built from the same source as these tests.

The two bugs a DAG-shaped test found that a chain-shaped one couldn't

Every test that existed before this session built chain-shaped graphs — matmul → add → relu → matmul → …. Writing a genuinely diamond-shaped test (a shared leaf feeding two independent fused branches a third node then combines) surfaced two real, previously-shipped bugs in the same afternoon:

  • A dangling pointer in the optimizer's replace(). It rewrote a fused node's inputs[] when one of its epilogue operands was itself later folded into something else, but not the redundant epilogue[].operand copy of the same pointer — which then dereferenced freed memory the next time the node executed. Segfaulted reliably on the repro.
  • An invalid execution order in gpu_execute. It derived its schedule by reversing a preorder traversal, which is only a valid topological order for a tree or chain — for a real DAG, a shared node can be scheduled after a consumer that needed it already uploaded. Replaced with a proper postorder traversal (graph_topo_order), shared with the autodiff module, which needs the identical guarantee in reverse.

Two more were found earlier the same session: a memory leak in multi-level constant folding (an intermediate const node superseded by a later fold was never freed — confirmed with an allocation trace, not just inspection), and unvalidated batch dimensions in matmul that could silently read past a smaller operand instead of erroring. All four now have permanent regression tests.

Performance

Where MiniXLA stands, honestly

Every number below is min of 20 timed launches after 10 warmup launches, itself the best of 4 full runs — this laptop GPU idles down to ~210 MHz between bursts and needs a few launches to ramp back up, which is real hardware behavior, not measurement noise to hide. MiniXLA GPU vs. CPU — the case for a compiler at all

Same operation (raw matmul), same machine. The GPU path gets meaningfully faster than CPU as the problem grows: 4.7× at 128×128 up to 47× at 1024×1024.

Raw matmul: MiniXLA vs. cuBLAS vs. PyTorch eager

GFLOPS achieved (higher is better) — log scale, because cuBLAS is 12–20× faster than MiniXLA's kernel at every size measured. cuBLAS uses Tensor Cores and multi-level tiling refined over years; MiniXLA uses a single-level 16×16/32×32 shared-memory tile with no tensor-core path. That gap is the honest state of Phase 4/5, not a claim to hide.

Does fusion actually help? A cleaner test than "vs. PyTorch"

Comparing MiniXLA's fused kernel against PyTorch's unfused 3-kernel sequence conflates two different questions — does fusion help, and is MiniXLA's raw kernel as efficient as cuBLAS's. Isolating the first: same tiled kernel infrastructure, matmul-only vs. matmul+bias+relu fused into the same launch. The epilogue's marginal cost is real (8–48% depending on size) but far cheaper than the two extra kernel launches and two extra global-memory round trips an unfused GPU implementation would pay — MiniXLA doesn't have an unfused GPU path to measure that against directly, which is itself the honest scope note.

What this does not show: MiniXLA's fused kernel is slower in wall-clock terms than PyTorch's unfused eager sequence at every size measured (2.3×–22.7×, worst at 512×512) — because the raw per-FLOP efficiency gap above dwarfs any launch-overhead savings at this kernel's current level of tuning. Fusion is working as designed; it isn't yet enough to close a 20× compute-efficiency gap on its own.

Methodology

How these numbers were produced

  • Timing. GPU: CUDA events around the operation only (no host-side setup in the bracket). CPU: batched wall-clock (clock()) — this platform's clock has ~15ms resolution, so small matmuls are timed in batches of up to 100 and divided, not timed individually.
  • Aggregation. GPU numbers are min of 20 runs (standard practice for GPU kernels — far less sensitive to transient clock-boost state than the median); CPU numbers are median of up to 20 batched samples. Every GPU number is additionally the best of 4 independent full runs of the suite, to average out this laptop's clock-boost variance between processes.
  • torch.compile was not available on this Windows machine — it requires Triton, which has no working Windows install here (verified: TritonMissing at compile time). PyTorch numbers are eager mode, which is what a real user gets on this platform without extra tooling.
  • Same random data, same seed scheme across all three systems per size; results are not cherry-picked runs.

Honest limitations

What isn't done, and why

Scope, not spin
  • The GPU kernel itself is unoptimized relative to cuBLAS — no tensor cores, no double-buffered shared memory, no vectorized loads, single-level tiling. This is the largest lever left; see the % of peak table above.
  • Broadcast bias-add is CPU-only. The PTX emitter and both GPU runtimes assume every fused epilogue operand is full-size; a broadcast (e.g. bias-vector) operand is detected and rejected with a clear error on GPU rather than silently computing a wrong answer, but isn't implemented there yet.
  • Multi-GPU is a design doc, not code. This machine has one physical GPU and no NCCL — real tensor/pipeline parallelism can't be built and verified here. Shipping untested distributed-systems code would be exactly the class of bug this session spent most of its time removing from already-shipped code. The architecture (ring all-reduce, Megatron-style column/row-parallel sharding, GPipe-style microbatching) is documented; single-GPU concurrent multi-stream scheduling is identified as the one piece that's honestly buildable here, and is future work.
  • No second-order gradients. Autodiff computes gradient tensors directly rather than building a differentiable backward graph — sufficient for training, not for meta-learning.
