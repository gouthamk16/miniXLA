What this is

Eight phases, six built and verified

MiniXLA takes a small tensor-op graph, rewrites it (constant folding, dead-node elimination, operator fusion into matmul+epilogue kernels), emits PTX for the fused regions, and runs it through the CUDA Driver API, with module caching and last-use buffer freeing. Phase 6 adds reverse-mode autodiff on top. A second pass (full writeup) then spent a session doing nothing but optimize the PTX kernel itself: 2D register blocking, vectorized shared-memory reads, larger tiles: 12.9% of cuBLAS to 53.0% at the kernel level, then a benchmarking-methodology fix (below) revealed the true number was higher still, 84.3%.

Correctness

27 tests, run against real hardware, not mocked

18 CPU tests (gcc, includes a ptxas-validated codegen check) and 9 GPU tests (nvcc, actually execute generated PTX on the RTX 4060 and compare against the CPU reference to 1e-4–1e-2 depending on scale, including two for the tensor-core kernel against a tolerance that scales with K — see the research doc). Every number in this report comes from a binary built from the same source as these tests.

The two bugs a DAG-shaped test found that a chain-shaped one couldn't

Every test that existed before this session built chain-shaped graphs: matmul → add → relu → matmul → …. Writing a genuinely diamond-shaped test (a shared leaf feeding two independent fused branches a third node then combines) surfaced two real, previously-shipped bugs in the same afternoon:

  • A dangling pointer in the optimizer's replace(). It rewrote a fused node's inputs[] when one of its epilogue operands was itself later folded into something else, but not the redundant epilogue[].operand copy of the same pointer, which then dereferenced freed memory the next time the node executed. Segfaulted reliably on the repro.
  • An invalid execution order in gpu_execute. It derived its schedule by reversing a preorder traversal, which is only a valid topological order for a tree or chain; for a real DAG, a shared node can be scheduled after a consumer that needed it already uploaded. Replaced with a proper postorder traversal (graph_topo_order), shared with the autodiff module, which needs the identical guarantee in reverse.

Two more were found earlier the same session: a memory leak in multi-level constant folding (an intermediate const node superseded by a later fold was never freed: confirmed with an allocation trace, not just inspection), and unvalidated batch dimensions in matmul that could silently read past a smaller operand instead of erroring. All four now have permanent regression tests.

Performance

Where MiniXLA stands, honestly

Numbers below are the median of 5–12 independent, process-isolated measurements per point (methodology and why that took two attempts to get right is its own story, right below the charts). The kernel itself improved 4.1× this session (2D register blocking, vectorized shared-memory reads, larger tiles: full writeup); fixing how it was measured moved the reported number by almost as much again, which is the more important lesson here.

Two benchmarking bugs, not one: the second one moved the headline number more

The first published version of this report measured MiniXLA's GPU time via gpu_execute, which re-uploads its inputs on every call: fair for measuring a full multi-kernel graph end to end, wrong for comparing raw kernel throughput against cublasSgemm timed around the call alone with operands already resident. Fixed with a dedicated kernel-only timing primitive (gpu_time_kernel_ms: upload once, time the launch, nothing else).

That fix alone didn't explain everything. Re-running the full sweep afterward reproducibly showed both cuBLAS and MiniXLA reading roughly 7× slower at exactly one size (512×512) than an isolated single-call measurement of the identical code, with GPU temperature ruling out thermal throttling and a 5×–15× larger warmup count not fixing it either. What did: running each (system, size) pair in its own fresh process instead of sharing one CUDA context across cuBLAS and MiniXLA calls. That's a real, reproducible cross-system interaction (allocator state or cuBLAS's internal heuristics reacting to something about sharing a context, not identified further), and it was inflating the gap between the two systems, not shrinking it: the honest comparison this fix produced is more favorable to MiniXLA than the flawed one, not less, which is exactly why it needed fixing rather than leaving alone.

MiniXLA GPU vs. CPU: the case for a compiler at all

Same operation (raw matmul), same machine. The optimized kernel widens this gap dramatically over the version in the first published report: 13× at 128×128 up to 557× at 1024×1024 (2048 CPU is untimed; the naive O(n³) loop would take tens of minutes for a number nobody needs).

Does fusion actually help? A cleaner test than "vs. PyTorch"

Comparing MiniXLA's fused kernel against PyTorch's unfused 3-kernel sequence conflates two different questions: does fusion help, and is MiniXLA's raw kernel as efficient as cuBLAS's. Isolating the first: same kernel infrastructure, matmul-only vs. matmul+bias+relu fused into the same launch. The epilogue's marginal cost is small and roughly flat now (0–15% depending on size, mostly under 4%): the vectorized-load work this session also made the epilogue itself cheaper to bolt on, not just the matmul faster.

The updated picture vs. PyTorch's unfused eager sequence (refreshed in a later session, process-isolated, matched warmup protocol on both sides after an early PyTorch reading turned out to be under-warmed for this GPU's clock-ramp behavior — see full writeup): MiniXLA's fused kernel is faster than PyTorch's unfused 3-kernel sequence at 128×128 (1.21×), small enough that per-launch overhead dominates and fusion's launch-count reduction wins outright, then behind at every larger size measured (1.10×–1.61×, worst at 512×512), converging back toward parity by 2048×2048. Fusion is a real, working lever; it's not yet enough on its own to beat a cuBLAS/cuDNN-backed unfused sequence once problems are big enough that raw compute efficiency dominates over launch overhead.

The real whole-range win: peak GPU memory, not speed

Same op (relu(matmul(a,b)+c)), same isolated methodology: MiniXLA's single fused kernel never materializes the two intermediate M×N tensors PyTorch eager's 3 separate ops each produce, so it uses less peak device memory at every size tested, not just the smallest. cuMemGetInfo delta around MiniXLA's real (unpooled) cuMemAlloc calls vs. PyTorch's own max_memory_allocated() — not identically-defined numbers (PyTorch's reflects its caching allocator's bookkeeping on top of the same raw need), but the real number each platform's user actually sees.

Methodology

How these numbers were produced

  • Process isolation, not one shared process. Every (system, size) pair (cuBLAS at 512, MiniXLA GPU at 1024, and so on) now runs via bench --pair <kind> <size>, a fresh process with its own CUDA context, launched and torn down before the next pair starts. Sharing one context between cuBLAS and MiniXLA calls turned out to produce a reproducible cross-system slowdown (see the panel above); isolation is the fix, and it's now the only mode these numbers are drawn from. The full-sweep single-process mode still exists for quick local iteration but its output is not what's reported here.
  • Timing. GPU: CUDA events bracketing the kernel launch only, after uploading inputs once: gpu_time_kernel_ms excludes host-side allocation and transfer, deliberately, so it's comparable to how cuBLAS is timed. CPU: batched wall-clock (clock()); this platform's clock has ~15ms resolution, so small matmuls are timed in batches of up to 100 and divided, not timed individually.
  • Aggregation: median, not min, of 5–12 isolated-process samples. A fresh process needs its own cold-start clock ramp-up (150 warmup launches, tuned by watching nvidia-smi's clock reading climb from an idle ~210MHz to boost ~1890MHz, not simply a function of warmup count, but of the process running long enough to reach steady state), and even after warmup, run-to-run variance across fresh processes is real (cuBLAS at 2048×2048 ranged 2.08–2.76ms across 12 samples). Reporting the median of several isolated runs, rather than the minimum of one run's internal repeats, is a deliberate choice to avoid quietly cherry-picking a lucky sample.
  • torch.compile was not available on this Windows machine: it requires Triton, which has no working Windows install here (verified: TritonMissing at compile time). PyTorch numbers are eager mode, which is what a real user gets on this platform without extra tooling.
  • Same random data, same seed scheme across all three systems per size; results are not cherry-picked runs.

Honest limitations

What isn't done, and why

Scope, not spin
  • The GPU kernel is 2D register-blocked with vectorized shared-memory reads (128×128 block tile, 8×8 per-thread output tile, transposed-A SMEM layout for ld.shared.v4.f32): still no tensor cores, no vectorized global loads, no warp tiling, no double buffering. That combination took the kernel from 12.9% to 53.0% of cuBLAS in isolated kernel-only timing (measured at 2048×2048; see gemm-optimization.md for the full autoresearch log). The remaining gap to cuBLAS's 84.3%-of-cuBLAS end-to-end number is a mix of: cuBLAS opportunistically running FP32 GEMM through TF32 tensor cores on this Ampere+/Ada GPU (a hardware-path difference no amount of CUDA-core tuning alone closes), and CUDA-core-level headroom this session identified but deliberately didn't attempt: global-load vectorization (needs a cooperative-load thread-mapping redesign), warp-level tiling, and mma.sync tensor-core paths, each scoped out because its failure mode is a plausible-looking wrong answer, not a build error, and this session's correctness-verification budget didn't stretch to cover it. Documented as unattempted, not abandoned.
  • Broadcast bias-add is CPU-only. The PTX emitter and both GPU runtimes assume every fused epilogue operand is full-size; a broadcast (e.g. bias-vector) operand is detected and rejected with a clear error on GPU rather than silently computing a wrong answer, but isn't implemented there yet.
  • Multi-GPU is a design doc, not code. This machine has one physical GPU and no NCCL: real tensor/pipeline parallelism can't be built and verified here. Shipping untested distributed-systems code would be exactly the class of bug this session spent most of its time removing from already-shipped code. The architecture (ring all-reduce, Megatron-style column/row-parallel sharding, GPipe-style microbatching) is documented; single-GPU concurrent multi-stream scheduling is identified as the one piece that's honestly buildable here, and is future work.
  • No second-order gradients. Autodiff computes gradient tensors directly rather than building a differentiable backward graph: sufficient for training, not for meta-learning.
